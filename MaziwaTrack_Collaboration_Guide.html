The Problem We Solve

💸 Late & Disputed Payments

Farmers wait months for payment with no independent record to dispute. Cooperatives keep records only in a clerk's book — no farmer-side copy.

🥛 290M Litres Wasted (2023)

KSh 14.7 billion lost because cooperatives only learn of surplus after milk arrives. No forecasting or daily trend data.

🏦 No Credit Access

Smallholder farmers can't get loans — daily deliveries prove income but no accepted documentation exists for lenders.

📋 Legal Compliance (May 2026)

Agriculture CS Mutahi Kagwe mandated per-farmer digital traceability records. Paper-based cooperatives face legal exposure.

Database Schema Reference

-- users
CREATE TABLE users (
  id          INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name        VARCHAR(100) NOT NULL,
  email       VARCHAR(150) UNIQUE NOT NULL,
  password    VARCHAR(255) NOT NULL,           -- bcrypt hash
  role        VARCHAR(10) CHECK (role IN ('farmer','grader','admin')) NOT NULL,
  is_active   BOOLEAN DEFAULT true,
  created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- deliveries
CREATE TABLE deliveries (
  id              INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  batch_number    VARCHAR(20) UNIQUE NOT NULL,
  farmer_id       INT REFERENCES users(id),
  declared_litres NUMERIC(8,2) NOT NULL,
  measured_litres NUMERIC(8,2),
  status          VARCHAR(20) CHECK (status IN ('pending','passed','rejected','flagged')) DEFAULT 'pending',
  grader_id       INT REFERENCES users(id),
  tested_at       TIMESTAMPTZ,
  notes           TEXT,
  created_at      TIMESTAMPTZ DEFAULT NOW()
);

-- payments
CREATE TABLE payments (
  id            INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  delivery_id   INT REFERENCES deliveries(id) UNIQUE,
  amount        NUMERIC(12,2) NOT NULL,         -- measured_litres × price_per_litre
  reference     VARCHAR(30) UNIQUE NOT NULL,
  status        VARCHAR(20) CHECK (status IN ('pending','approved','paid')) DEFAULT 'pending',
  admin_id      INT REFERENCES users(id),
  approved_at   TIMESTAMPTZ,
  created_at    TIMESTAMPTZ DEFAULT NOW()
);

-- audit_logs
CREATE TABLE audit_logs (
  id          INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     INT REFERENCES users(id),
  action      VARCHAR(100) NOT NULL,
  entity      VARCHAR(50),
  entity_id   INT,
  details     JSONB,
  created_at  TIMESTAMPTZ DEFAULT NOW()
);

Efficiency Recommendations

Use a single Express Router per role

Keep farmer.js, grader.js, admin.js separate. Mount them at /api/farmer, /api/grader, /api/admin. This maps 1:1 to React portal pages.

Centralise error handling

Add a single Express error-handling middleware at the bottom of index.js. All routes next(err) instead of sending their own error responses. Consistent JSON errors on every route.

React custom hook per portal

Create useFarmerData(), useGraderData(), useAdminData() hooks to encapsulate API calls. Keep portal JSX clean — data fetching out of the component.

PostgreSQL transaction blocks

Payment approval must be wrapped in a BEGIN/COMMIT transaction: update delivery status + insert payment + write audit_log — all three or none. Use pg's client transaction API.

Store JWT in httpOnly cookie

Never store JWTs in localStorage. Set httpOnly: true, sameSite: 'lax', secure: true (production). React reads role from a separate non-httpOnly userRole cookie for routing.

Validate on both sides

React: UI feedback (required fields, numeric checks). Express: server-side validation before any DB query. Never trust client input. Reject and return 400 with a clear message.

Golden Rules

Non-negotiable team agreements. These prevent the most common group-project failures before they happen.

Code Quality

No string concatenation in SQL — ever

Always use parameterized queries: db.query('SELECT * FROM users WHERE id = $1', [userId]). String-built queries will be flagged as an automatic fail by the lecturer (SQL injection).

Comment every non-obvious block

If someone else would spend more than 30 seconds understanding what your code does, add a comment. Especially on: middleware logic, complex SQL, PDF generation, and email templates.

Naming conventions — stick to them

JavaScript: camelCase for variables and functions. React components: PascalCase. DB columns: snake_case. Constants: UPPER_CASE. Never abbreviate unless universally clear.

No hardcoded secrets in code

All secrets (DB URL, JWT secret, email password) live in .env. Access via process.env.VARIABLE_NAME. The .env file is in .gitignore and is never committed.

Teamwork

Blocker? Shout within 24 hours

If you are stuck for more than a few hours, say so in the group chat immediately. Never sit quietly on a blocker and miss a deadline. The rest of the team can help unblock you.

Never merge your own PR

Open the PR, assign a reviewer, wait. If reviewer hasn't responded in 24 hours, ping them. Merging without review defeats the purpose of code review and can break main.

Keep the demo always runnable

main must always be in a state that runs cleanly after npm install and a fresh DB. Never merge broken code. Test locally first.

Everyone understands the whole system

You will be questioned on any part of the system during the final presentation, not just your own. At D3 and D4, markers may ask anyone about any part.

Communication Channels

WhatsApp / Group Chat

Day-to-day updates, quick questions, blocker alerts. Respond within 12 hours during weekdays.

GitHub Issues

Bug reports and feature sub-tasks. Assign to the relevant person. Close when merged.

GitHub Pull Requests

All code review happens here. Leave inline comments, not WhatsApp messages about code.

Shared Google Drive

Store deliverable documents, diagrams, wireframes. Anyone can view, relevant owner edits.

Escalation Protocol

Blocker Level 1: Stuck for < 24h

Try to solve it yourself. Use docs, StackOverflow, ChatGPT. If unresolved after ~3 hours, message the group chat.

Blocker Level 2: Team can't resolve

Post in group chat. If nobody can help within a day, schedule an emergency 30-min call. Pivot to another task in the meantime.

Scope Creep / Change Request

Any change to scope (new feature, tech change) must be agreed by all three members before implementation. No unilateral scope changes — they impact everyone's work.
